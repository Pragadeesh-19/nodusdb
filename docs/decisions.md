# Decisions

Every architecture decision of the project, D1 to D104, in order. The authorization-wedge decisions (D58 to D87)
are explained in [`designs/engineering-review-authz-wedge.md`](designs/engineering-review-authz-wedge.md), which is
the authority for their contracts. The Build Step 2 decisions (D88 to D104) are explained in
[`designs/engineering-review-build-step-2.md`](designs/engineering-review-build-step-2.md). The notes at the end
record what Build Step 1 settled while implementing them.

| D10 | Demotion threshold | Hysteresis: promote at 16, demote at 8 (`AdjacencyTable.DEMOTION_DEGREE`). Degrees 9–15 keep whichever tier the node already holds, so a node oscillating around 16 no longer allocates on every crossing | Ring 2 review, implemented |
| D11 | Buffer sizing contract | `kHop` excludes the start node. It throws `IllegalArgumentException` when the result exceeds `out.length`, rather than truncating silently. `commonNeighbors` requires `out.length ≥` the smaller degree | Ring 2 implementation |
| D12 | Initial allocation artifact | `GraphKernelAllocationTest` reads the thread's allocated-bytes counter across a primed steady-state window and asserts zero. The first measured window after warm-up allocates a fixed 72–96 bytes once, with no per-operation growth. Root cause not identified (probably a one-time JIT deoptimization) | Ring 2 verification |
| D13 | Batch slice access | `KHopTraversal` reads neighbors as a slice: `AdjacencyTable.neighborArray` plus `neighborBase`, fetched once per node, then `neighbors[base + i]`. This removes the per-neighbor method dispatch and bounds check from the hot loop | Ring 2 review, implemented |
| D14 | C-ABI signatures | The spec's signatures do not compile under GraalVM: every `@CEntryPoint` must take an `IsolateThread` as its first parameter. Every export therefore takes `graal_isolatethread_t*` first, and the Python loader creates the isolate with `graal_create_isolate` before its first call. Node ids are `long long` and output buffers are `long long*`, so they're 64-bit on Windows too | Ring 3 implementation, verified with a real build |
| D15 | Boundary errors | Each export catches `RuntimeException` and returns `false` or `-1`. Result buffers are filled up to `out_cap`, and the return value is the full count, so the caller can grow its buffer and retry. `OutputBufferTooSmallException` triggers the internal regrow in `GraphSession` | Ring 3 implementation |
| D16 | Handles | `GraphSessions` is a generation-checked handle table. A closed or stale handle is rejected, not reused. Access is synchronized. Each kernel is still single-writer, so one handle must not be used from two threads at once | Ring 3 implementation |
| D17 | Batch C-ABI | `nodus_add_edges_batch` and `nodus_remove_edges_batch` take two `long long*` columns and a count. The whole batch is validated before any edge is applied, so one bad node id leaves the graph unchanged and returns -1. The count is a caller contract: the C side cannot check the array length, so reading past the end is undefined behaviour | Phase 3 |
| D18 | Packaging | Native libraries are packaged into `python/nodusdb/bin/<os>-<arch>/`, which the loader searches first. CI builds on Linux, macOS, and Windows with GraalVM CE 22, runs the Java and Python suites, and uploads the library per OS. `pip install -e python/` works locally | Phase 3 |
| D19 | Lake key identity | The 64-bit key hash is the row identity. Two distinct keys with the same hash merge into one row. Collision probability is about n²/2⁶⁵ (about 3e-8 at one million keys). The caller supplies a well-mixed hash | Lake review (user decision) |
| D20 | Lake slab reclamation | Overwrites and deletes leave dead bytes. When an append does not fit, live bytes are copied into a power-of-two buffer of at least 2× the required size, reusing a spare buffer when possible. No flush exists yet, so this is the only reclamation path | Lake review (user decision) |
| D21 | Lake benchmark steady state | `DeltaMemTableBench` pre-sizes to one million rows and measures in-place upserts. Growth is excluded from the timed window, so the zero-allocation claim is testable with `-prof gc` | Lake review (user decision) |
| D22 | Lake documentation home | Design lives in the tracked `docs/lake.md`. `CLAUDE.md` is git-ignored, so it is a local reference only | Lake review (user decision) |
| D23 | Lake baseline | `DeltaMemTable.sustainedUpsert` on `windows-dev`: 227.4 ns/op (±6.2), about 4.4M upserts/s. `gc.count` 0 over the measured window, and `gc.alloc.rate.norm` 1.6e-4 B/op, which is harness background, not kernel allocation. Recorded in `bench/baseline/lake-windows-dev.json`. An exploratory run measured 243 ns/op (±118) and is superseded by this run | Lake baseline (D21) |
| D24 | Tombstones | Deletes never remove a row from the active buffer. They mark it `TOMBSTONE` in place, or append one. Removing the row would bring back an older committed version of the same key. Cost: a delete of an uncommitted key still writes a tombstone | Lake review (user decision, D1) |
| D25 | Parquet writer | Hand-written Parquet v1 on the JDK only: PLAIN, GZIP at level 1, REQUIRED columns. Chosen to keep the native image free of Hadoop | Lake review (user decision, D2) |
| D26 | Zero-copy export | Deferred. Heap arrays can move under native code, so zero-copy needs off-heap storage first. The flush copies at the boundary | Lake review (user decision, D3) |
| D27 | Catalog | Local manifest, Iceberg-shaped, replaced atomically. No Iceberg metadata or Avro manifests yet | Lake review (user decision, D4) |
| D28 | Backpressure | Writers never wait for a pending flush until the active buffer reaches 2× `maxRows` or 2× `maxSlabBytes`. Without the cap, memory grew without bound under overload | Lake flush benchmark |
| D29 | Buffer recycling | The frozen buffer is cleared on the flusher and reused as `spare`. Replacing it with a fresh buffer made the ingestion thread regrow arrays every cycle, about 216 B/op | Lake flush benchmark |
| D30 | Native CI verification | GitHub Actions run 37190865739 (commit 729b399) passed on Ubuntu, macOS (arm64), and Windows. Each job built `libnodusdb` with GraalVM CE 22 on JDK 22, ran 232 Java tests, and ran 38 Python tests against the library. The lake tests ran there, except the PyArrow comparison, which skips because the CI image has no `pyarrow`. JDK 25 was not tested, so T0.2 stays open | CI, verified by log review |
| D31 | WAL frame layout | Fixed 24-byte frames: operation (1 byte, 0x01 add, 0x02 remove), reserved (1 byte), zero padding (2 bytes), CRC32 (4 bytes, IEEE), source (8 bytes), destination (8 bytes). The CRC covers the operation and both IDs, not the padding. Header: ASCII `NODU` (0x4E4F4455), version 1 as a short, two reserved bytes, creation time as a long. Big-endian throughout. Eight-byte alignment, and a whole frame fits a cache line without splitting it | Ring 4 review (user decision) |
| D32 | Torn writes and corruption | Replay stops at the first frame that is incomplete or fails its CRC. The file is truncated to the end of the last good frame, and the number of removed bytes is reported. Corruption in the middle of the log drops every frame after it, as the spec requires. A partial tail is handled the same way as a checksum failure, so the 11-byte test is a partial frame, not a CRC failure | Ring 4 review |
| D33 | Snapshot format | Header: magic `NODS`, version 1, node capacity, edge count, creation time. Body: for each node, its outgoing degree and then its neighbors. Trailer: CRC32 over the body. Version 2 (D54) stores outgoing and incoming sections. Version 1 stored outgoing edges only, and the loader rebuilt incoming edges. The spec's raw 16-long block copy was replaced with a degree-prefixed list, which is smaller for low-degree nodes and needs no knowledge of the slab layout | Ring 4 implementation (deviation from spec, recorded) |
| D34 | Idempotent replay | Replaying the whole log over a snapshot gives the correct final state, because each edge's last operation decides whether it exists. A crash between the snapshot rename and the log reset therefore needs no generation counter. A test pins this case | Ring 4 review |
| D35 | Durability modes | ASYNC: a process kill loses only frames still in the buffer, and a power cut loses up to the flush interval (10 ms by default). SYNC: a single-edge call returns after its frame is forced to disk. Batch calls group-commit, so the log waits once per buffer of frames instead of once per edge. `sync()` makes everything accepted so far durable | Ring 4 review (user decision, D1) |
| D36 | Recovery target | The spec asks for sub-second recovery. Measured at 30.6M edges: 22.0 s in a fresh process (D54 measures 3.3 s), of which 0.13 s is replaying 500,000 frames. The target is not met, and the cost is in rebuilding the index structures from the snapshot. Storing the built layout would fix it, and that is a later design decision | Ring 4 benchmark |
| D37 | Benchmark integrity | A recovery timed inside the process that still holds the original graph measured garbage collection, not recovery (185 s and 131 s runs). Recovery is measured only in a fresh process. The digest of the recovered graph must match the digest taken before the crash | Ring 4 benchmark |
| D38 | Stale native copy | `python/nodusdb/bin/<os>-<arch>/` is searched before `target/native/`. After a local rebuild the packaged copy must be refreshed, or the loader keeps the old library. The copy is git-ignored | Ring 4 verification |
| D39 | Columnar ingress | Arrow columns are passed as buffer addresses and read in place. Nulls and text other than Arrow `string` are rejected. Offsets are validated for the whole batch before any row is applied, so a bad batch leaves the table unchanged | Ingest review (user request, bottleneck 1) |
| D40 | Parquet layout | Row groups of 122,880 rows, matching DuckDB's default. A column is dictionary-encoded when it has at most 65,536 distinct values and the dictionary plus indices are smaller than the plain values. Key columns are never dictionary-encoded, since keys are unique per buffer. Min and max are written in chunk metadata and page headers, with a declared type-defined column order. The deprecated min and max fields are written for numeric columns only. Doubles with NaN or zero carry no statistics | Measured on the taxi file with PyArrow and DuckDB, 2026-10-04 |
| D41 | Codec | Snappy is the default and matches DuckDB's default. It is implemented in Java, with a compressor that skips ahead after repeated misses. Snappy costs about a third of a 250,000-row flush on `windows-dev`. Uncompressed is available per table and produces files about 36% larger | Flush profile (JFR), user decision on codec as a table setting |
| D42 | Native aggregates | `nodus_lake_sum` and `nodus_lake_avg` cover the active buffer only, because the committed-file reader is a separate path. The loops use four independent accumulators. The incubating vector API was not used, because native-image support for it was not verified | Lake aggregate, user request |
| D43 | Flush path | `DeltaMemTable.clear` resets the index in one pass, not one removal per key. The writer reads column arrays directly, with no per-value method call. The key column skips the dictionary attempt | Flush profile (JFR) |
| D44 | Benchmark variants | W2 has a columnar-batch engine next to the single-call engine. W3 has an uncompressed engine next to the Snappy engine. W4 adds a native in-memory row and an ungrouped DuckDB row over the same columns. Engines are chosen per workload, and every fallthrough to SQLite is an explicit match. Results are in `bench/baseline/lake-heavyweights-windows-dev-v2.json` | Lake benchmark review |
| D45 | Key kinds | A graph is keyed by integers or by strings, never both. The first key type written claims the graph. The claim is stored in the `symbols.nodus` header, so a durable graph keeps it across restarts. A graph that already has edges but no symbol file is treated as integer-keyed. The check lives in the Python facade, so the integer C entry points keep their hot path | Phase 4 Module 1 review (decision made without user input, to confirm) |
| D46 | Symbol durability | A new string is written to `symbols.nodus` and forced before any edge that uses its id reaches the graph log. Batches group-commit to one force. A torn final record is truncated. A corrupt record before the end refuses to open, because an edge could then refer to the wrong string | Phase 4 Module 1 review |
| D47 | Interner concurrency | `StringInterner` uses one monitor. Graph writes come from one thread (D16), so the monitor is uncontended. A lock-free design was rejected: growth moves the slab, and the gain would not show in the single-writer path | Phase 4 Module 1 review |
| D48 | Concurrency model | One kernel-level seqlock covers every mutation and read. Per-adjacency-table versions were rejected, because they would duplicate the counter and split one invariant across many. Readers retry on overlap and take no lock. `GraphKernelConcurrencyTest` and `GraphConcurrencyTest` check it, and breaking the validation fails the stress test with a duplicated target | Phase 4 Module 2 review (user decision) |
| D49 | WAL format | Kept the 24-byte CRC32 frame (D31). The 27-byte frame with a `rel_type` field was rejected: the graph has one relation type, and a new layout would break durable directories. Torn-tail and checkpoint recovery stay as in D32 to D34. `TornWriteRecoveryTest` covers 100,000 edges followed by a 14-byte torn record | Phase 4 Module 3 review (user decision) |
| D50 | Release wheels | Each runner builds its own native library with GraalVM CE 22, and cibuildwheel packages it. `setup.py` declares an extension module, so the wheels carry platform tags. Linux wheels are tagged `manylinux_2_34`, because the library needs at most glibc 2.34. They install on Ubuntu 22.04 and later, Debian 12, and RHEL 9, but not on older distributions. cibuildwheel's build containers are `manylinux2014` (glibc 2.17), and pip there rejects any tag above 2.17. So Linux skips the in-container install test and smoke-tests the wheel on the `ubuntu-22.04` and `ubuntu-22.04-arm` hosts instead. macOS wheels target 11.0. `MACOSX_DEPLOYMENT_TARGET` alone did not change the version stamp the linker wrote, so the link also gets `-mmacosx-version-min=11.0`, and `build-native.sh` fails if the dylib's minos is not 11.0. Windows is unchanged. Publishing runs only on a published release, through PyPI trusted publishing. Passing in CI run 37272674367 (commit 72ca6f7): all five native jobs and all five wheel jobs. Earlier failures: `manylinux_2_35` was rejected inside the 2014 container, the image `quay.io/pypa/manylinux_2_34_*` does not exist, and macOS dylibs carried the runner SDK version (15.0, 14.0) | Phase 4 Module 4 review (user decision); revised after CI failures |
| D51 | Concurrent readers through C and Python | Calls on one handle are safe but serialized (D53). Readers do not run in parallel within a handle. Parallel readers need per-call scratch instead of the one buffer per session, which is a later phase | Phase 4 Module 2 finding; safety closed by D53 |
| D52 | Python thread safety | Every `Graph` and `LakeTable` in a process used to share one GraalVM isolate thread, which the runtime does not allow across OS threads. `_native.current_thread` now attaches one isolate thread per OS thread with `graal_attach_thread`. Public methods on `Graph` and `LakeTable` hold an `RLock`, which serializes calls and protects the per-handle result buffer. Mutation check: with the lock removed, the shared-reader test fails on every run. Tests: `test_concurrency.py`, `test_crash.py` (SIGKILL, every acknowledged sync write survives) | Release blocker review, 0.1.0rc1 |
| D53 | C-ABI handle safety | `GraphSession` had one result buffer, one edge staging buffer, and one key buffer per handle, plus an unguarded key-kind claim and close. Concurrent calls could return another call's results, stage edges that another batch overwrote, or race close. Every `GraphSession` method now holds the session monitor and checks a `closed` flag. The exports that stage-then-apply or compute-then-copy hold the same monitor. No ABI change. Tests: `GraphSessionConcurrencyTest` (mutation check fails with `ArrayIndexOutOfBoundsException`), `test_c_abi_concurrency.py` (batch variant fails on the pre-fix library every run; query variant passed three runs pre-fix, so it is not a reproduction) | D51 fix, 0cccc2c |
| D54 | Recovery build | Snapshot version 2 stores both sections, so the loader builds each node at its exact degree with no scatter pass. Recovery is a checksum pass, a scan that records each node's offset, a single-threaded prepare that sizes the slab and assigns blocks, then parallel fill tasks over disjoint node ranges. `prepareBulkLoad` and `loadBulkNode` skip the write sequence, so the kernel must not be shared until fill returns. Measured on this laptop at 30.6M edges, 3 GB heap: 29.1 s before, 3.3 s after with log replay, digest matches. Live heap after load is about 2.6 GB, roughly 88 bytes per edge, so G1 spends about 2 s copying survivors. Sub-second needs a smaller per-node layout (low-degree slab blocks are 128 bytes even at degree 1). Version 1 still loads. Version 2 is not readable by 0.1.0rc1 | R4.9 work, measured here |
| D55 | Native memory budget | `MemoryBudget` counts every native chunk (node table, low-degree slab, block pool) and refuses a request that would pass the limit with `MemoryLimitExceededException`, mapped to `NodusMemoryError` in Python. Growth is all-or-nothing: the bytes of every chunk a request needs are charged once before any is allocated. A write reserves its worst-case allocation (`reserveForAdd`) before it is journaled, so a rejected write never reaches the log and never changes the graph. Deletes never fail: demotion happens only when the slab can supply a block. A batch keeps the prefix it applied. Only native graph storage is counted, not the string table or result buffers on the Java heap. Chunks double, so the limit can trip with budget unused. C codes: `nodus_create_limited` and `nodus_open_durable_limited` report status through an int pointer, `nodus_add_edge` returns 1, 0, -1, or -3 | Release hardening for 0.1.0rc2 |
| D56 | Python handle lifetime | `Graph` and `LakeTable` keep the native handle in an `OwnedHandle` shared with a `weakref.finalize`, so a collected object releases its handle and emits a `ResourceWarning`. The `OwnedHandle` must not refer to its owner. `close()` detaches the finalizer, is idempotent, and keeps the handle when the native release fails so it can be retried | Release hardening for 0.1.0rc2 |
| D57 | CI Python suite and toolchain finding | Every CI job installs pytest and pyarrow and runs `python -m pytest python/tests`. `NODUSDB_REQUIRE_PYARROW` turns a missing pyarrow into a failure. The macOS arm64 job already ran the suite before this (67 tests, 6 skipped); it now runs 96 with none skipped. A local library built by GraalVM CE 23 ran `add_edge` in 1.2 ms against 9 microseconds on CE 22.0.2, with identical sources, so time a new toolchain before trusting it. Passing in CI run 37448322293 (commit e5c0e4c) | Release hardening for 0.1.0rc2 |

## Build Step 1 implementation notes

These were settled while building Step 1. Each one refines a frozen decision without changing a format.

| ID | Topic | Note |
|---|---|---|
| I1 | One apply path | Live writes and recovery share `RecordApplier`. The kernel is a state machine over the record stream, so a replayed log and a live write cannot diverge |
| I2 | Reservation | A transaction is validated, then its worst-case memory is reserved per touched node before anything is journaled. The headroom counts free blocks that can be reused, so a graph at its limit still accepts a write that reuses freed memory. Apply cannot fail on the budget |
| I3 | Batches | `add_edges_from` still applies one autocommit record per edge and keeps its prefix. The node table for the whole batch is reserved first, so a batch whose node ids do not fit is refused before any edge is applied |
| I4 | New directories | Creation writes the tripwire, opens the log, writes a first snapshot (so the erasure salt persists) and writes `FORMAT` last. A tripwire without `FORMAT`, `pre-v2/` or `.upgrade/` is a creation that did not finish and is reopened as new. This refines the version table in section 4.7 of the review |
| I5 | Upgrade readers | The version 1 readers never modify the old files. The old torn-tail truncation is not applied, so `pre-v2/` holds the original bytes. The backup is copied to `pre-v2.partial/` and renamed, so `pre-v2/` always means a complete copy |
| I6 | Upgrade log | The upgraded log holds the tenure `[EPOCH, TXN_COMMIT]`, then the key kind and the symbols as ordinary transactions chunked at the 1 MiB write limit. The review sketched one transaction, which cannot hold an unbounded symbol table |
| I7 | Schema retypes | A schema that flips the tupleset or retired flag of a relation that holds tuples is refused, at write and at replay. Moving the tuples between table pairs in the same transaction is deferred (see `TODOS.md`) |
| I8 | Checks | A check is a reachability search over `(node, definition)` frames. A grant found anywhere is returned. `CheckDepthException` is raised only when the depth limit stopped the search before it could decide, never as a silent `false` |
| I9 | Symbols | Symbol table chunks start at 4 KiB and double to 1 MiB, so a small memory limit is not exhausted by the first string. The table is native memory and counts toward `max_memory_mb`, which changes D55: strings are now inside the budget |
| I10 | C API | Failures return the codes of the error contract and keep their message for `nodus_last_error`. `nodus_check` returns 1, 0 or a negative code. Tokens come back through a pointer to two `int64` values |
| I11 | Parallel reads | Handle lookup is lock-free, reads take no monitor and use a result buffer per thread. Writes, checkpoint and close serialize on the session, and the Python object holds its lock for writes and close only. This closes D51 |
| I12 | Native performance gate | `python/benchmarks/native_ratio.py` times 200,000 `add_edge` and 200,000 `has_edge` inside the JVM and inside the native library, running the same Java code, and fails above a ratio. The review proposed 5. Measured on a laptop with GraalVM CE 22.0.2: about 9 for `add_edge` and 16 to 18 for `has_edge`, because ahead-of-time code is slower than JIT code for off-heap memory access. The default is 50, which passes that build and fails the CE 23 library (about 130 times slower than CE 22). Lower it once CI has a recorded baseline for GraalVM 25 |
| I13 | Single-tuple fast path | A tuple write whose nodes and tables already have room skips the memory reservation, appends one autocommit record and applies it without parsing it back. A write that must grow goes through the general transaction path. An addition that was just verified absent is inserted without a second membership test. Measured on one laptop on one day, at 200,000 edges through the native library: single-edge inserts 106,000 per second against 104,000 for the kernel before Step 1, batch 205,000 against 203,000, flat buffer 241,000 against 238,000. Before this path the new commit pipeline ran 13 to 30 percent slower |

| J1 | Native image spike | A throwaway program built with GraalVM CE 22.0.2 on Windows ran SHA-256, HMAC-SHA256, CRC32C, Ed25519 sign and verify (a tampered message was rejected), `HttpClient` over HTTP with an `If-None-Match` header, HTTPS with a CA bundle loaded from a PEM file, and HTTPS to the public S3 endpoint with the default trust store. MinIO could not be used: it stopped publishing community images in October 2025 and removed them from Docker Hub in September 2026. It differs from S3 in three ways that Step 2 absorbs: it lists a folder before sibling keys (our folders are flat), it drops empty metadata values (now refused on every backend), and it needs the key plus the prefix to stay under 1024 bytes (the key limit is now 512 and the prefix limit 256). Running on a laptop under Docker, its conditional-write race is slow, so that test shrinks there |
