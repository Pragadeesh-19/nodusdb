# CEO Plan: The authz race launch ("a Zanzibar check is a function call")

Generated by /plan-ceo-review on 2026-11-06 at `f4a4967`. Mode: SELECTIVE EXPANSION. Depth: strategy only.
The strategy it serves is [`relationship-lakehouse.md`](relationship-lakehouse.md): authorization plus audit as the
wedge, agent memory as the second market. An engineering review must clear this plan before any harness code.

## The claim

SpiceDB and OpenFGA are network services. To stay fast they cache, and their default modes accept a window of
stale answers (SpiceDB's `minimize_latency`, about 5 s by default). Their fresh modes cost a round trip to the
datastore on every check. Nodus holds the graph in the application's process, so a fully fresh check is a function
call. The launch measures that axis, latency at full freshness and time-to-revocation, and prints every row where
Nodus loses next to the rows where it wins.

No neutral, head-to-head check-latency benchmark of SpiceDB and OpenFGA existed when this was written; the numbers
in circulation are vendor-run (SpiceDB 5.76 ms p95 at 1M QPS on a dedicated CockroachDB cluster, Okta FGA p95 under
20 ms, the Zanzibar paper's p95 under 10 ms).

## Accepted scope

- **Act 1.** One union-only schema and one seeded Pareto dataset (S/M/L) in Nodus, SpiceDB and OpenFGA. Each engine
  runs in its own process and must give identical answers on a cross-check set before timing. Published per engine
  and consistency mode: p50/p99/p99.9 at full freshness and at the fastest mode; time-to-revocation in process and
  on a second machine (Nodus follower with and without a token); deep nesting with and without the reachability
  index; the losses in the same table: multi-machine freshness bounded by S3 (D66: about 200 to 500 ms), no lookups,
  one writer, Python only.
- **Act 2** (in this repository, since it has no second engine): the same writes landing in Iceberg `nodus_log` at
  a stated commit interval (default 60 s); "who could view X at T" timed through `as_of` and through DuckDB SQL,
  run before the erase because of D240; `erase` through `wait_erased` with a byte scan of every NodusDB-managed copy
  and bucket versioning off. The claim is limited as `docs/operations.md` ("What erasure cannot reach") limits it.
- **AuthzBench** as a separate neutral repository, a vendor guide, and a static leaderboard regenerated from raw
  JSON in CI, with every row naming the results commit and the nodusdb library's SHA-256.
- **Replay page**, static, every frame linked to its raw JSON.
- **Credibility rules.** One command reproduces everything on a rentable cloud VM; configs, schemas, seeds,
  container digests and raw JSON are public; every Nodus number is re-measured for the launch; competitors use
  their documented tuning and their maintainers get a review window before launch; a wrong number is corrected by a
  new results commit with a note, never edited in place.

Question D2:
D2 — R1: How should the benchmark issue checks when it measures latency percentiles?
Header: Load model
Options:
A) Open loop, fixed rates
Each engine gets checks on a fixed schedule at several rates, and latency is measured from when each check was due, recorded in HdrHistogram, in both drivers. Effort S, risk low, about 3 CC hours. ✅ p99 and p99.9 include the waiting a real application would see. ✅ Avoids the coordinated-omission critique that load-testing practice (wrk2, YCSB) answers the same way. ❌ Needs a rate sweep per engine, so a full run takes longer.
B) Closed loop, labelled service time
Issue the next check when the last returns and label the result "service time", not latency under load. Effort S, zero added work. ✅ Simplest driver; the numbers are honest because the label is. ✅ Fine for the per-check cost of an idle engine. ❌ The tail numbers say nothing about load, and HN will ask why p99.9 was measured this way.
C) Both, open loop as the headline (recommended)
Publish open-loop percentiles as the headline and closed-loop service time as a second table. Effort S, risk low, about 4 CC hours. ✅ Shows idle cost and behavior under load side by side. ✅ Readers who know the pitfall see it handled. ❌ Two tables per engine to explain.

Header: Topology

### 1. Architecture

```
  machine 1 (engines)                                  machine 2 (driver)
  ┌──────────────────────────────────┐   write/revoke   ┌──────────────────────────────────────────────┐
  │ Nodus writer process             │◄─────────────────┤ Go driver ──► SpiceDB, OpenFGA clients       │
  │  (adapter write endpoint)        │                  │ Python driver ──► Nodus follower (in process)│
  │ SpiceDB + Postgres               │◄── checks ───────┤   open-loop scheduler, closed-loop service    │
  │ OpenFGA + Postgres               │                  │   time, revocation timer, HdrHistogram        │
  └──────────────┬───────────────────┘                  └───────────────┬──────────────────────────────┘
                 │ ships log                                            │ raw JSON + manifest
                 ▼                                                      ▼
           bucket (SeaweedFS or S3) ──► follower polls          CI: schema check, results schema check,
                                                                calibration fake runs ──► static site
  one source schema (generator) ──► emits Nodus / SpiceDB / OpenFGA schemas (R3)
```
- Design twice. Shape 1 (the plan): an adapter per engine in its driver's language (load, write, check with a
  consistency mode and optional token, close) behind a driver that owns scheduling, timing and recording. Shape 2:
  every engine wrapped as a process speaking one bench protocol to a single Go driver. Shape 2 puts an IPC hop in
  front of every Nodus check, which contradicts S1 (Nodus in process) and blurs the headline. Pick: shape 1. It
  hides the timing policy, the part that must be right, behind a four-call surface each adapter implements.
- Red flags. 8 (hand-synced list): the three schemas, fixed by R3. 6 (two ways to do one task): the scheduler and
  recorder exist in Python and Go; the calibration fake in both drivers (S6) is the check that they agree, carried
  as required proof. 2 (information leakage): the results JSON is written by two drivers and read by the site;
  one results schema checked in CI for both drivers is the necessary implementation of D1's "validation moves
  into CI checks". No other flag applies.
- `[INFORMATIONAL] (confidence: 7/10) docs/designs/authz-race-launch.md:38-39` — R2 adds a write endpoint to the
  Nodus adapter on machine 1. It lives in the adapter, never in nodusdb, binds to the private interface of the
  run's network, and accepts writes only from machine 2. Necessary implementation of R2.
- Failure per path: the bucket becomes unavailable mid-run, so the follower stops advancing and the revoke is not
  observed; the cap reports "> cap" with the follower's `stats()` phase (CEO Section 2).
- Distribution: AuthzBench CI on GitHub Actions, pinned container digests, a Go module, the static site on a
  static host; the Nodus adapter pins a released wheel. Included in tasks T3, T6, T7.
