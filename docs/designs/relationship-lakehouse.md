## The secret

The warehouse is the wrong home for relationships, and the graph database is the wrong
home for history. Nobody owns the seam: a live relationship index inside the application
whose write-ahead log is an open lakehouse table. nodus already has both halves (graph
kernel, Spillway); today they share an allocator and nothing else.

## Vision

### 10x Check
One edge-change log, two views. The kernel applies each change in DRAM and answers
permission checks in microseconds, with nested-group reachability kept current
incrementally. Spillway commits the same changes as an Iceberg table, so Snowflake,
Databricks and DuckDB can query the full history with SQL. Followers on other machines
tail that table from S3 and serve local checks with no server to run. Any check can be
asked "as of" a past instant, and apps can subscribe to gained/lost-access deltas.

### Go-to-market
Wedge: Zanzibar-style authorization plus audit for companies past role tables. Second
market on the same engine: AI agent memory with provenance.

## Accepted Scope
- Typed, timestamped edges; WAL frame v2 with v1 replay compatibility
- Edge-change log committed by Spillway as real Iceberg (not the local manifest)
- Consistency tokens (log sequence numbers) on writes and checks
- Incremental reachability index with a measured per-update bound and fallback
- S3 single-writer commits, embedded followers tailing the log
- as_of(t) checks and k-hop
- Watch API delivering gained/lost-access deltas
- Agent-memory Python API

## Known pre-existing facts that shape the design
- `LakeTable` is a keyed upsert memtable (identity = 64-bit key hash); an append-only
  change log does not fit that model as-is.
- `Manifest` commits with a local ATOMIC_MOVE of manifest.txt; S3 has no rename.
- A kernel checkpoint replaces the WAL with an empty one (D33/D34), discarding history.
- GraphKernel stores (u, v) only: no relation type, no timestamp (D49 rejected rel_type).
