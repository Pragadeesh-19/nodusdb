# Lake suite on the 0.1.0 library: windows-dev

Machine: see bench/baseline/MACHINE.md. Measured on 2026-10-20 with python/benchmarks/benchmark_lake_heavyweights.py
(run, all workloads), the native library from the nodusdb 0.1.0 wheel on PyPI (GraalVM Community Edition 25.0.2),
Python 3.12.7, pyarrow 26.0.0 and DuckDB 1.5.6. Raw output: lake-heavyweights-release-windows-dev.json.
The previous suite (2026-10-04, library built by GraalVM CE 22.0.2) is lake-heavyweights-windows-dev-v2.json.

    NODUSDB_LIBRARY=<site-packages>/nodusdb/bin/windows-x86_64/libnodusdb.dll \
        python python/benchmarks/benchmark_lake_heavyweights.py run --out lake-heavyweights-release-windows-dev.json

same revenue total, and DuckDB scans them in the same time). Its write path and its native aggregate are not.

## Where the time goes: not found, but narrowed

1. A library built locally on 2026-10-07 (older than the wheel, built with GraalVM CE 22) is as slow: W1 25,622 rows/s
   and a W3 flush of 8.79 s. So this is not the Community Edition 25 toolchain, and not the wheel.
2. The same Java code on a plain JVM is fast. `DeltaMemTableBench.sustainedUpsert`, one fork, 3 warmup and 5
   measured iterations, JDK 22.0.2: 298.8 ns/op (error 6.8). The baseline in lake-windows-dev.json is 227 ns/op.
   That run is a smoke test, not a baseline.
3. `python/benchmarks/lake_native_probe.py` times the pieces through the wheel, 200,000 rows:

        upsert_table 200000 rows: 2.565 s, 77,965 rows/s
        sum over 200000 rows: 97.0 ms
        2000 single upserts: 25.6 us each
        flush 200000 rows: 6.645 s

   The native sum is a four-accumulator loop. At 97 ms for 200,000 rows it spends about 485 ns per element, which is
   hundreds of times what a compiled loop over memory costs.

The pattern (fast on a JVM, very slow in the native library, worst in loops that touch native columns element by
element) matches the symptom recorded for GraalVM CE 23 in docs/building.md: memory-segment access that the
native-image compiler does not optimize. The graph kernel also uses native memory and is only 6 to 14 times slower
than on a JVM, so the lake's access pattern is what differs. The cause is open work; see TODOS.md.

## Suspect

The lake was rewritten onto native memory on 2026-10-05, the day after the previous suite was measured at commit
3fdf779 (bench(lake): add columnar and uncompressed engines and a native aggregate row). The commits are c099214
through d823261, and 67061ff (fix(native): use GC-managed arenas so the native image can close memory) followed. The
2026-10-04 figures therefore describe the heap-array implementation, not the code in 0.1.0.
